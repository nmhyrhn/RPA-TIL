# [UiPath IXP] DU Classic·Modern 프로젝트와 모델 평가

## 1. 학습 주제

오늘은 Document Understanding 프로젝트에서 문서 유형과 추출 필드를 정의하고, 샘플을 어떻게 학습과 평가에 사용하는지 정리했다. 송장을 예로 들어 문서 유형은 Invoice, 필드는 송장번호·발행일·총액, 반복 항목은 품목명·수량·단가로 잡았다.

## 2. Classic의 Forms AI와 반정형 추출

| 방식 | 어울리는 문서 | 구성할 때 볼 부분 |
|---|---|---|
| Forms AI | 입력 위치가 일정한 양식 | 샘플에서 필드가 놓인 영역 지정 |
| 반정형 AI | 배치가 다른 여러 종류의 송장 | Document Manager에서 각 필드에 맞는 값 라벨링 |

폼의 같은 칸이 매번 같은 의미를 갖는다면 위치가 좋은 기준이 된다. 공급사에 따라 총액이 위쪽 요약란이나 아래쪽 합계란에 나온다면 여러 레이아웃의 샘플을 봐야 한다.

Document Manager에서는 샘플을 올리고 예측값이 원문과 맞는지 확인한다. 예측이 맞으면 확인하고, 잘못 잡힌 텍스트는 원문에서 올바른 값으로 바꾼다. 품목 행은 항목 값뿐 아니라 같은 행의 수량과 단가가 함께 묶였는지도 확인해야 한다.

## 3. 분류기와 추출기의 구성

| 구성 | 질문 | 결과 예시 |
|---|---|---|
| Classifier | 이 파일은 어떤 종류의 문서인가? | Invoice |
| Extractor | 이 유형에서 필요한 값은 무엇인가? | InvoiceNumber, IssueDate, TotalAmount |

송장과 발주서가 섞여 있다면 먼저 유형을 구분한 뒤 해당 유형의 추출 필드를 연결한다. Classic 프로젝트에서는 추출기와 분류기를 각각 준비하고 Studio에서 대응하는 설정을 선택하는 흐름으로 이해했다.

## 4. Modern 프로젝트의 빌드부터 게시까지

```text
빌드: 문서 형식·필드 정의, 샘플 추가, 예측 검토
→ 측정: 평가 데이터에서 유형별·필드별 결과 확인
→ 게시: 사용할 프로젝트 버전 생성
→ 모니터링: 프로젝트 성과 확인
```

빌드에서는 문서 유형과 필드를 먼저 정한다. 총액처럼 문서당 한 번 나오는 값과 품목 표처럼 반복되는 값의 구조를 구분해 두면 라벨을 일관되게 붙이기 쉽다. 게시한 뒤에는 Studio Web이나 워크플로우에서 의도한 프로젝트와 버전을 선택했는지 확인한다.

## 5. 평가용 문서를 따로 두는 이유

모델 수정 전후를 비교하려면 평가 문서와 정답 기준을 같게 유지해야 한다. 학습에 사용한 송장으로만 확인하면 처음 접하는 양식에서 어떤 필드가 틀리는지 파악하기 어렵다.

| 확인 항목 | 예시 |
|---|---|
| 문서 유형 | Invoice를 Purchase Order로 분류했는지 |
| 단일 필드 | 총액 대신 소계를 선택했는지 |
| 반복 필드 | 일부 품목 행이나 수량 열을 누락했는지 |
| 양식별 편차 | 특정 공급사의 송장에서 오류가 반복되는지 |

## 6. Helix 분류와 복습 메모

Modern 프로젝트에서 Helix를 문서 분류에 사용하는 경우에는 문서 유형을 구성하고 샘플로 분류 결과를 확인한 뒤, 게시한 버전을 Studio 연동에 사용한다. 유형별 평가 결과와 필드별 평가 결과를 함께 보면 오류가 분류부터 시작됐는지 좁혀 갈 수 있다.

게시 전에는 문서 유형, 정답 라벨, 평가 데이터, 연결할 버전을 순서대로 다시 확인한다.
