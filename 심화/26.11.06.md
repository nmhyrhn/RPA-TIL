# [UiPath 심화] REFramework 구조와 Queue·DataRow 처리 흐름

## 1. 학습 주제

마지막으로 REFramework의 전체 흐름을 정리했다. 앞에서 배운 예외 처리, Config, 워크플로우 분리, Queue가 하나의 구조 안에서 연결되는 부분이다.

처음부터 파일을 전부 외우기보다 `준비 → 한 건 가져오기 → 처리 → 다음 건 또는 종료` 순서로 따라가면서 각 파일이 맡는 일을 정리했다.

## 2. Sequence, Flowchart, State Machine

| 형태 | 흐름을 표현하는 방식 |
|---|---|
| Sequence | 작업을 순서대로 배치 |
| Flowchart | 조건과 분기를 흐름도로 연결 |
| State Machine | 현재 상태와 조건에 따라 다음 상태로 이동 |

주문 예제는 주문 접수, 결제, 제조, 완료 상태를 연결한다. 결제에 실패하면 결제 상태로 돌아가는 것처럼, 현재 결과에 따라 다음 위치가 달라진다.

REFramework도 State Machine을 기반으로 한다. 무조건 아래로 내려가는 순서가 아니라, 결과에 따라 초기화로 돌아가거나 다음 항목을 가져온다.

## 3. Dispatcher와 Performer

Queue를 사용하는 업무에서는 데이터를 넣는 역할과 실제 처리하는 역할을 나눌 수 있다.

```text
Dispatcher
  원본 데이터 수집
  → 처리 대상 선정
  → Queue 등록

Performer
  Queue에서 한 건 가져오기
  → 실제 업무 처리
  → 처리 결과 기록
```

ACME 예제로 보면 WI5 항목의 WIID를 Queue에 넣는 쪽이 Dispatcher, WIID를 꺼내 상세 페이지에서 업무를 수행하는 쪽이 Performer에 해당한다.

REFramework는 이런 항목별 처리에 필요한 초기화, 예외 처리, 상태 기록 구조를 제공한다. Queue만 사용할 수 있는 것은 아니며 DataRow 방식도 다룬다.

## 4. 네 가지 State

| State | 역할 | 다음 흐름 |
|---|---|---|
| Initialization | 설정 읽기, 앱 준비, 로그인 | 준비가 되면 데이터 가져오기 |
| Get Transaction Data | 다음 처리 항목 가져오기 | 항목이 있으면 처리, 없으면 종료 |
| Process Transaction | 한 건의 업무 수행과 결과 기록 | 결과에 따라 다음 건 또는 초기화 |
| End Process | 앱 종료와 마무리 | 종료 |

정상 흐름을 글로 그리면 다음과 같다.

```text
Initialization
  → Get Transaction Data
      → 항목 있음: Process Transaction
          → 처리 후 다시 Get Transaction Data
      → 항목 없음: End Process
```

Process Transaction에서 시스템 예외가 발생하면 초기화로 돌아가 환경을 다시 준비하는 흐름을 갖는다. 재시도 여부와 횟수는 설정과 사용하는 데이터 방식에 맞춰 확인해야 한다.

## 5. Initialization에서 하는 일

초기화 단계에서는 Config와 실행 환경을 준비한다.

| 워크플로우 | 역할 |
|---|---|
| InitAllSettings.xaml | 설정을 읽고 Config 구성 |
| InitAllApplications.xaml | 브라우저 실행, 로그인 등 업무 환경 준비 |
| KillAllProcesses.xaml | 필요한 경우 지정한 프로세스 종료 |

Config가 이미 로드되어 있는지 확인하는 이유는 시스템 오류 후 Initialization에 다시 들어올 수 있기 때문이다. 최초 설정 읽기와 재접속 때 필요한 작업을 구분해야 한다.

프로세스 종료 작업도 대상 이름을 명확히 정해야 한다. 재초기화가 필요하다고 현재 열려 있는 모든 앱을 무조건 종료하는 식으로 이해하지는 않는다.

Config는 설정값, 상수, Asset 이름을 나누어 관리한다. 실제 시트 이름과 키는 사용하는 템플릿에 맞춰 확인한다.

## 6. TransactionItem과 TransactionNumber

`TransactionItem`은 현재 처리 중인 한 건이다. `TransactionNumber`는 처리 순서를 관리할 때 사용하는 번호이며 전체 데이터 개수와 구분해야 한다.

| 변수 | 의미 |
|---|---|
| TransactionItem | 현재 처리할 항목 |
| TransactionNumber | 현재 처리 순서를 관리하는 번호 |
| Config | 실행 설정 Dictionary |
| SystemException | 시스템 예외 정보 |
| BusinessException | 업무 예외 정보 |
| RetryNumber | 재시도 횟수 관리 |

현재 항목이 없을 때는 TransactionItem을 Nothing으로 두고 종료 흐름으로 연결한다. 이 종료 조건을 빠뜨리면 마지막 데이터를 반복하거나 없는 항목에 접근할 수 있다.

## 7. Process Transaction의 세 가지 결과

업무 로직은 Process.xaml에서 한 건 단위로 처리한다. 이후 SetTransactionStatus.xaml에서 결과 기록과 관련 처리를 수행한다.

| 결과 | 흐름 |
|---|---|
| Success | 성공 기록 후 다음 항목 조회 |
| Business Exception | 업무 실패 기록 후 다음 항목 조회 |
| System Exception | 시스템 실패 처리 후 초기화 흐름으로 이동 |

하위 워크플로우가 예외를 잡고 로그만 남긴 채 끝내면 프레임워크가 실패를 알지 못할 수 있다. 첫날 정리한 Rethrow가 여기서 연결된다. 상위에서 처리해야 할 예외는 그대로 전달해야 한다.

또한 시스템 예외가 났다고 현재 업무가 아무것도 수행되지 않았다고 단정할 수 없다. 저장은 완료됐는데 다음 화면 확인에서 실패했을 수도 있다. 재시도 시 같은 건을 중복 처리하지 않을 기준도 필요하다.

## 8. Queue 방식으로 ACME 데이터 처리

Asset으로 로그인 정보를 가져오고 WI5 항목의 WIID를 Queue에 등록한다. 이후 한 건씩 꺼내 상세 페이지로 이동한다.

```text
Config와 Asset 읽기
→ 로그인 및 Work Items 추출
→ WI5 대상 선정·Queue 등록
→ Get Transaction Item
→ 현재 항목의 WIID 읽기
→ 상세 페이지 이동
→ 상태 기록
```

Queue Item에 `WIID`라는 키로 값을 넣었다면 다음처럼 읽을 수 있다.

```vb
in_TransactionItem.SpecificContent("WIID").ToString
```

키 이름은 등록할 때와 읽을 때 같아야 한다.

실습처럼 초기화 과정에 Queue 등록을 넣는 경우에는 재초기화 때 같은 항목이 또 등록되지 않는지 확인해야 한다. Dispatcher와 Performer를 분리해서 생각하면 수집·등록과 복구·재실행의 역할을 구분하기 쉽다.

## 9. Orchestrator 없이 DataRow로 처리

Queue 대신 추출한 DataTable의 행을 한 건씩 처리할 수도 있다. WI5 행을 골라 DataRow 배열로 보관한다.

다음은 그 흐름을 설명하기 위한 표현식이다. `dt_WorkItems`는 추출 결과, `WIID_List`는 DataRow 배열이다.

```vb
WIID_List = dt_WorkItems.Select("Type = 'WI5'")
```

이때 TransactionItem 형식을 QueueItem에서 DataRow로 바꾼다. Main 변수만 바꾸고 끝내면 안 된다.

- GetTransactionData의 출력 인수
- Process의 입력 인수
- SetTransactionStatus 등 관련 인수
- Invoke Workflow File의 인수 연결
- Queue 전용 조회·상태 기록 부분

위 항목들을 함께 맞춰야 한다. 비-Queue 방식에서도 성공과 실패를 남길 방법은 필요하다.

## 10. DataRow의 종료 조건과 인덱스

처리 번호를 1부터 시작한다면 배열 인덱스는 0부터 시작하므로 하나를 빼서 가져온다.

아래는 GetTransactionData의 분기를 설명하는 VB 형태의 예시다. Studio에서는 If와 Assign으로 구성할 수 있다.

```vb
If in_TransactionNumber <= WIID_List.Length Then
    out_TransactionItem = WIID_List(in_TransactionNumber - 1)
Else
    out_TransactionItem = Nothing
End If
```

처리할 행을 받았다면 WIID는 다음처럼 읽는다.

```vb
in_TransactionItem("WIID").ToString
```

Queue 방식의 `SpecificContent`와 접근 방식이 다르다. 대상이 0건인 경우, 마지막 행까지 처리한 경우에도 종료 조건이 맞는지 확인해야 한다.

## 11. End Process와 복습 메모

End Process에서는 로그아웃, 브라우저 종료 등 마무리 작업을 수행한다. 업무에 따라 결과 저장이나 알림을 연결할 수도 있다.

이번 범위는 앞에서 배운 내용이 어디에 쓰이는지 연결해서 보는 것이 좋았다.

```text
Config: 실행 설정 준비
인수: 파일 사이 데이터 전달
Queue 또는 DataRow: 처리할 한 건 표현
예외 처리: 실패 원인 전달과 다음 흐름 결정
REFramework: 위 작업을 상태별로 배치
```

다시 볼 때는 정상 처리, 업무 예외, 시스템 예외, 처리 대상 0건의 네 가지 경우를 각각 따라가 볼 것. 파일 이름을 외우는 것보다 다음 State로 이동하는 이유를 설명할 수 있어야 한다.
