# [UiPath 심화] 예외 처리와 디버깅, Throw와 Rethrow

## 1. 학습 주제

자동화가 정상적으로 실행되는 순서만 작성하면 파일이 없거나 화면이 늦게 뜨는 상황에서 작업이 끊긴다. 오늘은 이런 상황에서 어떤 정보를 남기고, 어디에서 다음 동작을 결정할지 정리했다.

학습 순서는 예외 구분 → 디버깅 → Try Catch → Throw와 Rethrow → 실행 전 검사이다.

## 2. 시스템 예외와 업무 예외

예외를 구분하는 이유는 대응 방법이 다르기 때문이다.

| 구분 | 상황 | 처리할 때 볼 것 |
|---|---|---|
| System Exception | 파일을 찾지 못함, 페이지 접근 실패, UI 요소 탐색 실패 | 환경을 복구하면 다시 처리할 수 있는가 |
| Business Exception | 필수값 누락, 허용되지 않는 금액 | 데이터가 업무 조건을 만족하는가 |

예를 들어 주문 금액이 0원인데 양수만 허용하는 업무라면, 브라우저를 다시 켜도 금액은 바뀌지 않는다. 이런 건 업무 예외로 구분하고 원인을 기록해야 한다.

반대로 페이지 로딩 실패는 잠시 기다린 뒤 재시도할 수 있다. 다만 시스템 예외라고 모두 재시도로 해결되는 것은 아니다. 잘못된 파일 경로는 경로를 고쳐야 한다.

## 3. 디버깅은 값이 달라지는 지점을 찾는 과정

오류 메시지만 보고 원인을 추측하기보다, 문제가 생기는 액티비티 앞에 중단점을 두고 실행 흐름을 확인한다.

1. 확인할 액티비티에 Breakpoint를 설정한다.
2. 디버그 실행으로 해당 위치에서 멈춘다.
3. 파일 경로, DataTable, 현재 행처럼 다음 작업에 들어갈 값을 확인한다.
4. 한 단계씩 진행하며 값과 분기 결과를 살펴본다.
5. 예상과 달라지는 첫 지점을 찾는다.

예를 들어 파일 읽기에 실패했다면 파일이 없는지 확인하기 전에, 경로 변수에 실제로 어떤 문자열이 들어 있는지부터 보는 편이 빠르다.

## 4. Try Catch의 실행 순서

| 영역 | 넣는 작업 |
|---|---|
| Try | 파일 읽기, 웹 접근 등 예외가 발생할 수 있는 작업 |
| Catch | 예외 기록, 복구, 상위 전달 등 예외별 대응 |
| Finally | 정상 처리와 예외 처리 뒤에 필요한 정리 작업 |

```text
Try
  Read Range Workbook: 존재하지 않는 파일 읽기
Catch
  Write Line: 오류 메시지 출력
Finally
  Write Line: 정리 단계 출력
```

Catch에서 출력할 표현식은 다음과 같다.

```vb
"오류 발생 : " + exception.Message
```

Try 중간에서 예외가 발생하면 남아 있는 Try 작업을 계속하는 것이 아니라, 해당 예외를 처리할 Catch로 이동한다. 처리 가능한 Catch가 없다면 예외는 상위로 전달된다.

Finally는 일반적인 예외 처리 흐름에서 성공 여부와 관계없이 실행된다. 다만 로봇 프로세스 자체를 강제 종료한 상황까지 정리 작업을 보장한다고 생각하면 안 된다.

## 5. Throw: 업무 조건을 만족하지 않을 때 예외 발생

업무 규칙은 액티비티가 알아서 판단하지 않는다. 조건을 직접 검사하고, 조건을 어겼을 때 Throw로 예외를 발생시킨다.

```vb
Amount <= 0
```

If의 Then에 Throw를 넣고 Exception 속성에 아래 표현식을 지정한다.

```vb
New BusinessRuleException("금액이 올바르지 않습니다.")
```

Write Line으로 메시지만 출력하면 다음 액티비티가 그대로 실행될 수 있다. Throw를 사용하면 현재 흐름을 중단하고 예외 처리 쪽으로 넘길 수 있다.

## 6. Rethrow: 잡은 예외를 상위로 전달

워크플로우를 여러 파일로 나누면 하위 파일에서 실패해도 전체 작업의 실패 여부는 상위에서 결정해야 할 수 있다.

```text
Main.xaml
  Try
    Invoke Workflow File: ReadFile.xaml
  Catch
    최종 실패 처리

ReadFile.xaml
  Try
    파일 읽기
  Catch
    오류 로그 기록
    Rethrow
```

ReadFile.xaml의 Catch에서 로그만 남기고 끝내면 Main.xaml은 호출이 정상적으로 끝난 것처럼 다음 작업으로 넘어갈 수 있다. Rethrow는 현재 잡은 예외를 다시 전달해 이 상황을 막는다.

| 액티비티 | 용도 |
|---|---|
| Throw | 지정한 예외를 발생시킨다 |
| Rethrow | Catch에서 잡은 예외를 그대로 다시 전달한다 |

하위에서는 어떤 작업이 실패했는지 남기고, 상위에서는 재시도할지 종료할지 결정하는 식으로 역할을 나눌 수 있다.

## 7. 유효성 검사와 Workflow Analyzer

유효성 검사는 필수 속성, 표현식, 인수 형식 등 실행에 필요한 구성을 확인한다. Workflow Analyzer는 이름 규칙이나 사용하지 않는 변수처럼 설정된 품질 규칙도 검사한다.

둘 다 실행 전에 확인할 수 있지만 실제 파일 존재 여부나 로그인 성공까지 보장하지는 않는다. 검사 통과와 실행 성공은 따로 확인해야 한다.

## 8. 복습 메모

예외 처리를 넣었다고 해서 실패가 해결되는 것은 아니다. Catch 이후에 계속 진행해도 되는지를 먼저 정해야 한다.

다시 볼 때는 아래 흐름을 직접 설명해 볼 것.

- 파일 읽기 실패 후 Catch와 Finally가 실행되는 순서
- 금액이 0일 때 Throw가 필요한 이유
- 하위 Catch에서 Rethrow를 뺐을 때 상위 흐름이 달라지는 이유
