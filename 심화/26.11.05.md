# [UiPath 심화] Orchestrator 배포와 실행, Asset과 Queue

## 1. 학습 주제

Studio에서 만든 자동화를 운영하려면 실행할 PC, 계정, 시간, 처리 결과를 함께 관리해야 한다. Orchestrator에서 프로세스를 배포하고 실행하는 순서와 Asset, Queue의 역할을 정리했다.

메뉴 이름을 따로 외우기보다 `게시한 패키지가 어떤 환경에서 실행되는가`를 기준으로 보면 연결하기 쉽다.

## 2. Orchestrator에서 관리하는 것

| 항목 | 역할 |
|---|---|
| Tenant | 자동화 자원과 관리 설정을 구분하는 단위 |
| Folder | 업무별 자원과 접근 권한을 묶는 공간 |
| Machine | 로봇이 실행될 컴퓨터와 연결할 인프라 설정 |
| Package | Studio에서 게시한 프로젝트 묶음과 버전 |
| Process | 실행할 패키지와 버전 등을 연결한 구성 |
| Job | 프로세스를 실제로 실행한 작업 |
| Trigger | 시간이나 큐 조건에 따라 실행을 시작하는 설정 |

Package, Process, Job은 구분해서 봐야 한다. 패키지가 올라왔다고 실행이 끝난 것은 아니다. 해당 패키지를 사용하는 프로세스를 만들고 실행하면 Job이 생성된다.

## 3. Attended와 Unattended

Attended는 사용자가 작업하는 환경에서 사람의 실행과 개입을 전제로 사용하는 방식이다. Unattended는 지정한 실행 환경에서 사람의 직접 조작 없이 업무를 수행하는 방식이다.

무인 실행에서는 Studio에서 잘 돌아가는지만 확인해서는 부족하다. 실행 계정, 머신 연결, 권한, 런타임 같은 조건도 맞아야 한다.

## 4. 배포 전에 실행 환경 연결

1. Tenant에서 머신 템플릿을 만든다.
2. 실행 계정의 접근 권한과 Unattended 설정을 준비한다.
3. Folder를 만들고 사용할 사용자와 머신을 연결한다.
4. UiPath Assistant에서 Orchestrator 연결을 설정한다.
5. 연결 상태와 사용할 라이선스를 확인한다.

머신 키 연결을 사용한다. 연결이 되었더라도 Studio 개발 권한과 무인 실행에 필요한 권한은 따로 확인한다.

## 5. 게시부터 Job 확인까지

```text
Studio 프로젝트 게시
→ Orchestrator에서 패키지와 버전 확인
→ Folder 안에 Process 생성
→ 수동 실행 또는 Trigger 설정
→ Job 상태와 로그 확인
```

시간 트리거에서는 반복 주기뿐 아니라 실행 계정과 머신, 시간대도 확인한다. 원하는 시간이 오전 9시라면 어떤 시간대를 기준으로 9시인지가 맞아야 한다. 휴무일 제외가 필요하면 비영업일 설정과 트리거에 적용된 조건도 함께 본다.

배포 후에는 실행 결과를 Job에서 확인한다. 실패했다면 게시 성공 여부와 실행 실패 원인을 섞어서 판단하지 않는다.

## 6. 수정한 프로세스를 반영할 때

프로젝트를 수정하면 새 버전으로 게시하고, Orchestrator의 프로세스가 사용할 버전을 확인한다.

```text
프로젝트 수정
→ 새 패키지 버전 게시
→ Process의 패키지 버전 업데이트
→ 실행 결과 확인
```

게시 후 프로세스 메뉴에서 최신 항목을 사용하도록 업데이트한다. 새 패키지를 올렸다는 사실만 보고 기존 프로세스까지 바뀌었다고 생각하면 안 된다.

## 7. Asset: 실행에 필요한 설정 관리

Asset은 로봇이 실행할 때 필요한 값을 Orchestrator에서 관리하는 기능이다.

| 형식 | 용도 예시 |
|---|---|
| Text | URL, 일반 문자열 설정 |
| Boolean | 기능 사용 여부 |
| Integer | 횟수 같은 정수 설정 |
| Credential | 사용자 이름과 비밀번호 |

일반 설정은 Get Asset, 계정 정보는 Get Credential로 가져온다. 비밀번호는 일반 Text에 적어 두지 않고 Credential 형식으로 구분한다.

지난 시간의 Config와 연결하면, Config에는 조회할 Asset 이름을 두고 실제 운영 값은 Orchestrator에서 읽는 구조로 사용할 수 있다. Asset이 있는 폴더와 로봇의 접근 권한도 맞아야 한다.

## 8. Queue와 Transaction

Queue는 처리할 업무 항목을 모아 두는 대기열이다. 주문 목록을 처리한다면 주문 한 건을 Queue Item 하나로 나눌 수 있다.

Transaction은 그 항목을 가져와 처리하는 시도로 이해했다. 전체 파일을 한 번 실행하는 것과 주문 한 건의 성공 여부를 기록하는 것은 서로 다른 단위다.

기본 흐름은 다음과 같다.

```text
Add Queue Item: 처리할 데이터 등록
→ Get Transaction Item: 항목을 가져와 처리 시작
→ 업무 수행
→ Set Transaction Status: 성공 또는 실패 기록
```

등록된 항목은 New, 처리 중에는 In Progress, 결과에 따라 Successful 또는 Failed로 관리할 수 있다. 로봇이 예기치 않게 중단되어 처리 상태가 마무리되지 않는 경우에는 Abandoned 상태도 확인하게 된다.

Get Queue Items로 목록을 조회하는 것과 Get Transaction Item으로 처리할 항목을 가져오는 것은 구분해야 한다. 업무 처리 예제에서는 후자의 흐름을 기준으로 본다.

## 9. 실패 항목을 재시도하는 기준

| 실패 유형 | 예시 | 재시도 판단 |
|---|---|---|
| Business Exception | 필수 고객 번호 누락 | 같은 데이터로 반복해도 해결되지 않음 |
| Application Exception | 일시적 앱 오류, 연결 실패 | 환경이 복구되면 처리할 가능성이 있음 |

Queue의 자동 재시도는 설정과 예외 유형에 영향을 받는다. Application Exception이라고 무조건 무제한 재시도하는 것은 아니다. 자동 재시도 사용 여부와 최대 횟수를 확인해야 한다.

Business Exception은 기본 자동 재시도 대상에서 제외되는 흐름으로 이해했다. 원본 데이터를 고치거나 담당자가 확인해야 할 일을 단순 재시도로 넘기지 않는 것이 중요하다.

## 10. 시간 트리거와 큐 트리거

시간 트리거는 정해진 시각이나 주기에 맞춰 실행한다. 큐 트리거는 처리할 항목의 수 등 Queue 조건에 따라 실행한다.

큐 트리거를 설정할 때는 실행을 시작할 항목 수와 생성할 작업 수, 보류·실행 작업 수 제한을 함께 본다. 항목 하나가 들어올 때마다 반드시 Job 하나가 생긴다고 생각하면 설정을 잘못 해석할 수 있다.

## 11. 복습 메모

Asset은 실행에 필요한 설정이고 Queue는 처리할 업무 데이터다. Process는 실행 구성이며 Job은 실제 실행 기록이다. 이 두 쌍을 구분하니 메뉴 역할이 좀 더 명확해진다.

복습할 때는 주문 한 건을 기준으로 등록, 처리 시작, 결과 기록, 실패 후 판단까지 설명해 볼 것.
