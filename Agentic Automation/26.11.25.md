# [UiPath Agentic Automation] BPMN·DMN과 Maestro 송장 검증 흐름

## 오늘 정리한 내용

구매 승인 업무를 예로 두니 BPMN과 DMN의 역할이 구분됐다. BPMN에는 요청 접수부터 검토와 승인까지의 순서를 이벤트, 태스크, 게이트웨이로 표현한다. 금액과 요청 유형에 따라 어느 승인 절차를 적용할지 정하는 기준은 DMN 결정표로 정리할 수 있다.

## 대표 실습 — 송장과 구매주문서 대조

- 시작 조건 — 문서 데이터를 준비하는 RPA, 두 문서를 비교하는 에이전트, 사람 검토용 Action App을 준비한다.
- 구성 — RPA의 송장·구매주문서 JSON을 각각 `in_InvoiceData`, `in_PurchaseOrderData`에 매핑한다.
- 분기 — 비교 결과로 검토 필요 여부를 판단하고, 검토 결과의 승인·거절 값으로 후속 작업을 선택한다.
- 예상 결과 — 승인된 검토 건은 Data Fabric에 기록되고, 거절된 건은 Gmail을 통해 통지된다.

```text
문서 데이터 준비 → 에이전트 비교 → 검토 필요 여부 판단
                                   ├ 일치 → 정상 경로
                                   └ 불일치 → 사람 검토
                                              ├ 승인 → Data Fabric 기록
                                              └ 거절 → Gmail 통지
```

## 응용 실습 — 판단 조건을 표로 써 보기

| 비교 결과 | 사람 검토 결과 | 후속 작업 |
|---|---|---|
| 일치 | 해당 없음 | 정상 경로 진행 |
| 불일치 | 승인 | 검토 건 기록 |
| 불일치 | 거절 | 거절 통지 |

표로 정리해 보니 비교 결과가 비어 있을 때의 경로도 필요하다. 사람 검토로 넘기는 경우에는 어떤 문서를 비교했고 어느 항목이 달랐는지 화면에 표시하면 담당자가 원문과 대조하기 쉽겠다.

## 구성 메모

| 구성 | 역할 | 확인할 데이터 |
|---|---|---|
| RPA 프로세스 | 송장·구매주문서 데이터 준비 | 문서별 JSON |
| Agent | 품목·수량 등 대조 | 일치 여부와 차이 |
| 독점 게이트웨이 | 조건에 맞는 경로 선택 | 비교 결과 또는 승인 값 |
| Action App | 사람 검토 접수 | 문서 정보, 불일치 사유, 결정 |
| Gmail / Data Fabric | 통지 또는 기록 | 수신자와 본문 / 엔터티 필드 |

## 증상별 점검

- 에이전트가 한쪽 문서를 읽지 못함 — RPA 출력과 에이전트 입력이 올바른 순서로 매핑됐는지 확인한다.
- 검토가 필요한데 정상 경로로 진행함 — 비교 출력의 자료형과 게이트웨이 조건을 확인한다.
- 승인이나 거절 뒤 결과를 찾기 어려움 — 실행 이력에서 선택된 경로를 확인하고, 승인 건은 Data Fabric 레코드에서, 거절 건은 Gmail 발송 결과에서 확인한다.
- 검토 완료 후 후속 단계가 실행되지 않음 — Action App 출력의 실제 값과 분기 조건을 대조한다.
- 기록 저장이 실패함 — 필드 매핑과 텍스트 길이 제한을 확인한다.

## 오늘의 정리

송장 검증 흐름에서 다시 볼 부분은 두 번의 분기다. 첫 번째는 에이전트가 반환한 문서 비교 결과로 검토 필요 여부를 판단한다. 두 번째는 담당자의 승인·거절 값으로 기록과 통지 중 어느 작업을 진행할지 정한다. 흐름을 따라가며 각 분기가 실제로 어떤 출력값을 읽는지 확인하면 매핑 오류를 찾기 쉽겠다.
