# [UiPath Agentic Automation] Agent Builder로 입력·도구·평가 설계하기

## 오늘 정리한 내용

Agent Builder에서 먼저 구분해 둔 것은 공통 지침과 실행할 때마다 바뀌는 값이다. 시스템 프롬프트에는 역할과 제약, 출력 기준을 적는다. 사용자 프롬프트에는 이번 요청을 적고 고객 요구사항이나 주문 번호처럼 건마다 달라지는 입력 인수를 연결한다.

주문을 조회하는 예시로 생각하면 역할이 더 분명하다. 에이전트는 어떤 도구가 필요한지 판단하고 그 결과를 정리한다. 정해진 절차대로 주문 시스템을 조회하는 부분은 RPA 워크플로를 도구로 연결해 맡길 수 있다.

## 대표 실습 — 제품 추천 에이전트

- 시작 조건 — 고객 요구사항을 입력 인수로 받고, 제품 목록을 Storage Bucket에 올려 인덱스를 구성한다.
- 구성 — 인덱스를 Context Grounding에 연결하고, 사용자 프롬프트에서 고객 요구사항 인수를 참조한다.
- 출력 기준 — 요구 조건을 만족하는 제품을 최대 세 개 제시하고 제품별 추천 근거를 붙인다. 적합한 제품이 없으면 그 사실을 반환하도록 지시한다.
- 예상 결과 — 예산과 필수 기능을 바꿔 실행하면 조건에 따라 추천 결과가 달라진다.

```text
고객 요구사항 → 관련 제품 검색 → 조건 확인 → 추천 결과와 근거 반환
```

## 응용 실습 — 주문 상세 조회

주문 상세 조회 흐름에서는 `OrderID`가 도구의 조회 조건으로 들어가고, 조회 결과가 `OutputDescription`으로 나온다. 주문 번호가 비어 있거나 해당 주문이 없을 때는 어떤 메시지를 반환할지도 프롬프트에 적어 두면 좋겠다. 담당자 확인이 필요한 경우에는 Action App에 주문 번호와 확인 사유를 함께 전달하는 흐름으로 생각할 수 있다.

## 구성 메모

| 구성 | 담당하는 일 | 확인할 값 |
|---|---|---|
| 입력·출력 인수 | 실행 데이터 주고받기 | 값, 데이터 형식, 매핑 |
| Context Grounding | 내부 자료에서 관련 내용 검색 | 인덱스와 검색 결과 |
| 도구 | 외부 조회나 RPA 실행 | 호출 인수와 응답 |
| 가드레일 | 허용 범위와 제약 적용 | 정책 적용 여부 |
| 평가 집합 | 여러 입력으로 결과 비교 | 기대 출력과 평가 기준 |

## 증상별 점검

- 입력한 조건이 답변에 반영되지 않음 — 사용자 프롬프트가 입력 인수를 참조하는지 확인한다.
- 제품 목록에 없는 항목을 추천함 — 연결한 인덱스와 검색 결과를 확인하고, 근거가 없는 경우의 출력 기준을 보완한다.
- 주문 조회가 실패함 — 도구 호출 로그에서 주문 번호와 연결 상태를 확인한다.
- 조회는 성공했지만 답변에 주문 정보가 빠짐 — 도구 응답에 필요한 필드가 있는지, 그 값이 최종 출력에 반영되는지 차례로 확인한다.
- 디버그는 성공하지만 평가 점수가 낮음 — 기대 출력, 평가 기준, 비교 대상 출력 인수를 각각 확인한다.

## 오늘의 정리

제품 추천은 고객 조건을 잘 읽는지, 주문 조회는 도구에 정확한 번호를 넘기는지가 관건이다. 디버그에서는 한 건의 입력과 도구 호출을 따라가 보고, 평가 집합에는 정상 입력과 예외 입력을 함께 넣어 결과를 비교할 수 있다.
